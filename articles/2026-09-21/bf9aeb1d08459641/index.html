App RouterとRSCで築く高パフォーマンス設計

報道zenn.dev2026.09.21

Next.js 13以降で導入された「App Router」は、React Server Components(RSC、サーバー側でレンダリングされるコンポーネント)をデフォルトのコンポーネントタイプとして採用しています。RSCはクライアント側のJavaScriptバンドルサイズに影響を与えないため、「パフォーマンス最適化の最大の鍵」になると解説されています。サーバー側で直接データベースやAPIからデータを取得でき、APIキーなどの機密情報も安全に扱えます。

一方でRSCにはuseStateやuseEffectといったReact Hooks、windowやlocalStorageなどのブラウザAPIが使えないという制限もあります。設計上は「クライアント境界をできるだけ下位にプッシュすることで、クライアントに送信されるJavaScriptの量を最小限に抑える」ことが重要だと紹介されています。

キャッシング機構についても整理されています。同じfetchリクエストが複数回呼び出されても一度だけ実行される「Request Memoization」、指定秒数キャッシュした後に再検証するrevalidateオプション、そしてrevalidatePathやrevalidateTagによるオンデマンドの再検証が組み合わさることで、高パフォーマンスな設計が実現できるとまとめられています。

出典が伝えている要点

  • App RouterはNext.js 13以降で導入された新しいルーティングパラダイムである
  • App RouterはReact Server Componentsをデフォルトのコンポーネントタイプとして採用している
  • Server Components (RSC) はクライアント側のJavaScriptバンドルサイズに影響を与えない
  • RSCはTime To Interactive (TTI) の改善に寄与する
  • RSCはサーバー側で直接データベースやAPIからのデータフェッチが可能である
  • RSCはAPIキーなどの機密情報をサーバー側で安全に扱える
  • RSCでは useState や useEffect などのReact Hooksは使用できない
  • RSCでは window や localStorage などのブラウザAPIは使用できない
  • Request Memoizationという機構により、同じfetchリクエストは複数回呼び出されても一度だけ実行される
  • revalidateオプションを設定すると、指定秒数キャッシュした後に再検証される
  • revalidatePathとrevalidateTagという関数でオンデマンドの再検証が可能である
