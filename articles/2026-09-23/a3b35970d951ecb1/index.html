GitHub API未認証レート制限、共有IPでの429リスク

体験談zenn.dev2026.09.23

筆者はVercel Functions上で稼働する自作Webアプリから、GitHub APIを未認証で呼び出しています。未認証リクエストの上限は60回/時間ですが、この制限は呼び出し元IPアドレス単位でカウントされる仕様です。Vercelのようなサーバーレス環境は複数の利用者・アプリで送信元IPを共有することがあるため、自分のリクエスト頻度が低くても他者の呼び出しと合算されて上限に達し、429エラーになりうると気づいたことを紹介しています。

「自分の呼び出し頻度と無関係に429が返りうる。『1時間に1回だから引っかからない』は、自分のリクエストだけを数えた見積もりでした」と振り返っています。対策として、API取得に失敗した場合は前回取得済みのデータを保持し続ける設計に変更したとのことです。

本記事は2026年9月1日時点の実測に基づくもので、筆者はまだ実際に429エラーを経験したわけではなく、運用を続けた上で追記する予定だとしています。対処法の一つとしてPersonal Access Token（GitHubの個人用アクセストークン）を使えば上限が5000回/時間に上がる方法もありますが、今回は未採用とのことです。

出典が伝えている要点

  • GitHub APIの未認証リクエストは、送信元IPアドレスに紐づけてレート制限がカウントされる仕様である
  • GitHub APIの未認証リクエストの上限は60回/時間である
  • 筆者はVercel Functionsなどサーバーレス環境からGitHub APIを未認証で呼び出している
  • Vercel Functions等のサーバーレス環境は複数の利用者・アプリで送信元IPを共有することがある
  • 共有IPの場合、自分のリクエスト頻度が低くても、同じIPを使う他者の呼び出しと合算されて上限に達し429エラーになりうる
  • リポジトリ情報1件を取得した際のレスポンスサイズは約6.0KBだった
  • 筆者はAPI取得に失敗した場合、前回取得済みのデータを保持し続ける設計に変更した
  • データ更新処理はdelete→insertを同一トランザクション内で実行しており、分離して実行すると表示が空になるリスクがあるとしている
  • 本記事の実測時点は2026年9月1日である
  • 筆者は記事執筆時点で実際に429エラーを経験したわけではなく、運用を続けた上で追記する予定だとしている
  • 対処法の一つとしてPersonal Access Tokenを使えば上限が5000回/時間に上がる方法があるが、筆者はこれを未採用としている
