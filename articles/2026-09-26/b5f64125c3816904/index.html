モノレポNext.jsのビルドキャッシュ問題、原因は自前構成だった

体験談zenn.dev2026.09.26

Cloudflare Workers Buildsで、npm workspacesを使った15アプリ構成のモノレポNext.jsアプリをビルドする際に「ビルド出力キャッシュが非対応」というエラーが表示される問題に著者は直面しました。調査の結果、これはCloudflare側の制約ではなく、モノレポ構成側の問題だったと判明します。

Next.js 16では既定でビルド時のTurbopackキャッシュ（turbopackFileSystemCacheForBuild）が無効になっている点、Workers Buildsがビルドコマンド実行前に自前で依存をインストールする仕様である点が絡んでいました。対処として①Turbopackのビルド時キャッシュを有効化、②各アプリのキャッシュディレクトリをルートと往復させる、③ルートのpackage.jsonにnextを追加、の3点を実施しています。

段階的な改善の結果、npm ci削除で247.7秒（−14.5%）、並列化で223.5秒（−8.7%）を経て、本番環境でのビルド時間は182.5秒から85.5秒（−53%）まで短縮されました。

出典が伝えている要点

  • 対象環境はNext.js 16、npm workspacesを使ったモノレポ（apps/*配下に15アプリ）、Cloudflare Workers Builds
  • 改善前のビルド全体は289.8秒、ビルド計は198.0秒だった
  • npm ciを削除したところ247.7秒になった（−14.5%）
  • ビルドを並列化したところ223.5秒になった（−8.7%）
  • 並列化の効果が期待より小さかったのは2コアの制限によるものと記事は説明している
  • キャッシュを有効化したところ、保存回は201.1秒、復元回は75.2秒になった
  • キャッシュサイズは547MB（15アプリ×36MB）だった
  • 本番環境でのビルド時間は182.5秒から85.5秒に短縮された（−53%）
  • Next.js 16の既定値では、turbopackFileSystemCacheForBuildはfalse（ビルド時は無効）に設定されている
  • Cloudflare Workers Buildsはビルドコマンドを実行する前に自分で依存をインストールする仕様である
  • 著者が打った対処は、Turbopackのビルド時キャッシュを有効化すること、各アプリのキャッシュをルートと往復させること、ルートのpackage.jsonにnextを追加することの3つである
