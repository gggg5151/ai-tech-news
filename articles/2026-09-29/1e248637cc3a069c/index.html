Next.js 16のmiddleware移行、codemodが拾えない落とし穴

体験談zenn.dev2026.09.29

個人開発者の「こそあど」氏が、自身が同一リポジトリから運用する3つのマッチングアプリ（SparMate、NetaPair、BoardLink、いずれもVercel運用）でNext.js 16のmiddleware→Proxy API移行を行った際の落とし穴を報告しています。

Next.js 16ではmiddlewareが新しいProxy APIに置き換わり、デフォルトの実行環境がEdge Runtime（CDNのエッジサーバー上で動く軽量な実行環境）になります。公式のcodemod（コードを自動変換するツール）はexport const runtime = 'edge'という宣言を自動的に削除しますが、middleware.tsとproxy.tsの共存は許可されないため、段階的な移行ができません。筆者が試したところ、同一リポジトリの3プロジェクトすべてがビルドエラーになったといいます。

さらに厄介なのは、lib/auth-guard.tsのような型注釈ファイル内にあるNextMiddleware型の参照をcodemodが自動修正してくれない点です。筆者はgrep -r "NextMiddleware|MiddlewareConfig"のようなコマンドで、codemodが見落とした箇所を手動で洗い出すことを勧めています。Next.js 16への移行を控えている方は、ビルドを通しただけで安心せず型ファイルまで確認することが必要そうです。

出典が伝えている要点

  • 筆者は「こそあど」という個人開発者である。
  • 筆者は同一リポジトリからSparMate、NetaPair、BoardLinkという3つのマッチングアプリを運用している。
  • これら3つのアプリはVercelで運用されている。
  • Next.js 16ではmiddlewareがProxy APIに移行する。
  • Proxy APIはEdge Runtimeがデフォルトになる。
  • 公式のcodemodはexport const runtime = 'edge'という宣言を自動的に削除する。
  • Next.js 16ではmiddleware.tsとproxy.tsの共存が許可されない。
  • 筆者が段階的移行を試みたところ、同一リポジトリの3プロジェクトすべてがビルドエラーになった。
  • codemodはlib/auth-guard.tsのような型注釈ファイル内のNextMiddleware型参照を自動修正しない。
  • 記事はgrep -r "NextMiddleware|MiddlewareConfig"のようなコマンドで、codemodが見落とした箇所を検出することを提案している。
