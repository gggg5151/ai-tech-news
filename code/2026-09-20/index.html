supabase/supabase の apps/design-system/hooks/use-config.ts を読む

GitHub で実物を見る ↗2026.09.20

SupabaseはPostgresを中核にしたBaaS基盤で、このファイルは公式デザインシステム(shadcn/ui系サイト)の設定管理フックです。「ユーザーが選んだテーマやレイアウト設定をページ遷移してもブラウザ再訪問しても覚えている」という、Next.jsアプリでよくある要件を、わずか30行で実装しています。TypeScriptの型テクニックと、状態管理ライブラリjotaiの実用パターンが両方詰まっているため教材に選びました。

コード

import { useAtom } from 'jotai'
import { atomWithStorage } from 'jotai/utils'
import { ComponentProps } from 'react'
import { SonnerToaster } from 'ui'

import { Style } from '@/registry/styles'
import { Theme } from '@/registry/themes'

// import { BackendProvider } from '@/registry/backend-provider'

type Config = {
  style: Style['name']
  theme: Theme['name']
  radius: number
  sonnerPosition: ComponentProps<typeof SonnerToaster>['position']
  sonnerExpand: boolean
  // backendProvider: BackendProvider['name'] | undefined
}

const configAtom = atomWithStorage<Config>('config', {
  style: 'default',
  theme: 'zinc',
  radius: 0.5,
  sonnerPosition: 'bottom-right',
  sonnerExpand: false,
  // backendProvider: 'nextjs-auth',
})

export function useConfig() {
  return useAtom(configAtom)
}

引用はリポジトリの実物と機械で照合しています。「// …略…」は省略した行です。

上から順に読む

import { useAtom } from 'jotai'
import { atomWithStorage } from 'jotai/utils'

jotaiはReactの「グローバル状態管理」ライブラリです。ReactのuseStateはそのコンポーネント内でしか使えませんが、jotaiの`atom`（ここでは`atomWithStorage`）はコンポーネントの外で状態の入れ物を1つ作り、それをどのコンポーネントからでも`useAtom`で読み書きできます。Reduxの軽量版のようなものだと考えてください。`atomWithStorage`は普通のatomと違い、値をブラウザのlocalStorageにも自動保存してくれる特別バージョンです。

import { ComponentProps } from 'react'

`ComponentProps`はReactが用意している「型を作るための道具（ユーティリティ型）」です。あるコンポーネントが受け取れるprops（属性）の型一覧を、そのコンポーネントの実装を見に行かなくても取り出せます。例えば`ComponentProps<typeof Button>`と書けば、Buttonコンポーネントが受け付ける全propsの型が手に入ります。後の行で実際に使われています。

import { Style } from '@/registry/styles'
import { Theme } from '@/registry/themes'

`@/`から始まるパスはこのプロジェクト独自の「エイリアス（別名）」で、プロジェクトルートからの絶対パスを意味します（`../../`のような相対パスの書き換えを避けるためNext.jsでよく設定されます）。ここでは他のファイルに定義された`Style`型と`Theme`型を読み込んでいます。中身を見なくても、「スタイルの種類」「テーマの種類」を表す型が別ファイルにある、という前提で読み進めれば大丈夫です。

type Config = {
  style: Style['name']
  theme: Theme['name']
  radius: number
  sonnerPosition: ComponentProps<typeof SonnerToaster>['position']
  sonnerExpand: boolean
}

`type Config = { ... }`は「Configという名前の型（オブジェクトの形の設計図）を定義する」という宣言です。この設定オブジェクトが持つべきプロパティと、それぞれの型を列挙しています。1行1プロパティで、`プロパティ名: 型`という書き方はTypeScriptの基本形です。

// backendProvider: BackendProvider['name'] | undefined

行頭の`//`はコメントで、実行には一切影響しません。このコードは「将来backendProviderという設定項目を足すかもしれない」というメモとして残されたコメントアウト済みの行です。もし生きていたら`型A | 型B`という「ユニオン型（AまたはBのどちらか）」の書き方になっていて、「BackendProviderのname、または値が無いことを表すundefined」を意味します。実務のコードには、こうした未使用の下書きがそのまま残っていることがよくあります。

style: Style['name']

`Style['name']`は「インデックスアクセス型」と呼ばれる書き方です。`Style`という型（おそらくオブジェクトの型）の中から、`name`というプロパティだけの型を取り出しています。JavaScriptで`style.name`と書けば値を取り出せるのと似た感覚で、TypeScriptでは`Style['name']`と書くとその値の「型」だけを取り出せます。こうすることで、Style型の定義が変わっても、Config側は自動的に追従します。

sonnerPosition: ComponentProps<typeof SonnerToaster>['position']

1行に3つのテクニックが重なっています。まず`typeof SonnerToaster`で「SonnerToasterというコンポーネントの型そのもの」を取得します（`typeof`は値から型を逆算するTypeScriptの演算子です）。次に`ComponentProps<...>`でそのコンポーネントが受け取れるprops全体の型を取り出します。最後に`['position']`のインデックスアクセスで、その中の`position`というprop（トースト通知を画面のどこに出すか）の型だけに絞り込んでいます。他のライブラリの型定義を直接コピーせず「借りてくる」ことで、ライブラリ側の仕様変更にも追従できる、実務でよく使うテクニックです。

const configAtom = atomWithStorage<Config>('config', {

`atomWithStorage<Config>`の`<Config>`は「この関数が扱う状態の型はConfigですよ」とジェネリクス（山括弧で型を指定する仕組み）で明示しています。第1引数の`'config'`はlocalStorageに保存するときのキー名です（ブラウザの開発者ツールでlocalStorageを覗くと`config`というキーで値が入っているのが見えます）。このあとに続く第2引数がその状態の初期値で、Config型の形に沿ったオブジェクトになっています。

export function useConfig() {
  return useAtom(configAtom)
}

最後に、これまで作った`configAtom`を直接コンポーネントに公開せず、`useConfig`という自作フックで包んでいます。`useAtom(configAtom)`は`[現在の値, 更新用の関数]`という配列を返すので、呼び出し側は`const [config, setConfig] = useConfig()`のように使えます。なぜ`useAtom(configAtom)`をそのまま使わせないのか？　こうしておけば、将来jotaiから別の状態管理ライブラリに乗り換えたくなっても、このファイルの中身だけ書き換えれば良く、アプリ全体で`useConfig()`を呼んでいる箇所は一切変更せずに済みます。「外部ライブラリを直接あちこちで使わず、自分のフックで一枚ラップする」というのは実務で非常によく使われる設計判断です。
