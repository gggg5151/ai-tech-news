wonderwhy-er/DesktopCommanderMCP の src/utils/withTimeout.ts を読む

GitHub で実物を見る ↗2026.09.22

DesktopCommanderMCPは、Claudeにターミナル操作やファイル検索、diffベースのファイル編集能力を与えるMCP（Model Context Protocol）サーバーです。AIがファイル読み込みやPDF解析など「いつ終わるか分からない」処理を大量に呼び出すため、「時間切れになったら諦めて既定値を返す」ユーティリティが要になっています。今回はその中核であるwithTimeout関数を読みます。Promiseの基本パターンと、非同期処理特有の「二重解決」というバグをどう防ぐかを学べる、コンパクトで実践的なコードです。

コード

/**
 * Executes a promise with a timeout. If the promise doesn't resolve or reject within
 * the specified timeout, returns the provided default value.
 *
 * @param operation The promise to execute
 * @param timeoutMs Timeout in milliseconds
 * @param operationName Name of the operation (for logs)
 * @param defaultValue Value to return if the operation times out
 * @returns Promise that resolves with the operation result or the default value on timeout
 */
export function withTimeout<T>(
    operation: Promise<T>,
    timeoutMs: number,
    operationName: string,
    defaultValue: T
): Promise<T> {
    // Don't sanitize operation name for logs - only telemetry will sanitize if needed
    return new Promise((resolve, reject) => {
        let isCompleted = false;

        // Set up timeout
        const timeoutId = setTimeout(() => {
            if (!isCompleted) {
                isCompleted = true;
                if (defaultValue !== null) {
                    resolve(defaultValue);
                } else {
                    // Keep the original operation name in the error message
                    // Telemetry sanitization happens at the capture level
                    reject(`__ERROR__: ${operationName} timed out after ${timeoutMs / 1000} seconds`);
                }
            }
        }, timeoutMs);

        // Execute the operation
        operation
            .then(result => {
                if (!isCompleted) {
                    isCompleted = true;
                    clearTimeout(timeoutId);
                    resolve(result);
                }
            })
            .catch(error => {
                if (!isCompleted) {
                    isCompleted = true;
                    clearTimeout(timeoutId);
                    if (defaultValue !== null) {
                        resolve(defaultValue);
                    } else {
                        // Pass the original error unchanged - sanitization for telemetry happens in capture
                        reject(error);
                    }
                }
            });
    });
}

引用はリポジトリの実物と機械で照合しています。「// …略…」は省略した行です。

上から順に読む

export function withTimeout<T>(
    operation: Promise<T>,

関数名の直後にある `<T>` はジェネリクス（型引数）です。「この関数はどんな型でも受け取れるが、受け取った型と返す型は連動する」ということを表します。例えば `withTimeout<string>(...)` として呼べば、`operation` は `Promise<string>`、`defaultValue` は `string` だと型チェッカーが理解します。1つの関数を色々な型（数値でも文字列でもオブジェクトでも）で使い回すためのTypeScriptの仕組みです。

timeoutMs: number,
    operationName: string,
    defaultValue: T
): Promise<T> {

引数は4つ。`operation`は「これから実行したい非同期処理そのもの」（Promise型の値）、`timeoutMs`は制限時間（ミリ秒）、`operationName`はログ用の名前、`defaultValue`はタイムアウト時に代わりに返す値です。関数全体の戻り値の型 `Promise<T>` は「T型の値でいつか解決されるPromiseを返す」という意味で、この関数自体が非同期関数として扱われます。

return new Promise((resolve, reject) => {

これは「Promiseエグゼキューター」と呼ばれる定番パターンです。`new Promise(...)` に渡す関数（コールバック）は自動的に2つの関数 `resolve` と `reject` を受け取ります。`resolve(値)` を呼べばこのPromiseは成功として確定し、`reject(理由)` を呼べば失敗として確定します。中身のコードは、いつ・どんな条件でresolveやrejectを呼ぶかを自分で組み立てる場所です。

let isCompleted = false;

`let` は再代入可能な変数を宣言するキーワードです。このフラグは「このPromiseはもう決着がついたか」を覚えておくためのものです。なぜ必要かというと、この後「タイマーが先に発火する」ケースと「元の処理が先に終わる」ケースの2つが競争していて、両方がresolve/rejectを呼んでしまうとPromiseの仕様上おかしなことになる（実際には2回目以降は無視されますが、意図が読みにくいコードになる）ため、明示的に「もう処理済みか」を見て制御しています。

const timeoutId = setTimeout(() => {
            if (!isCompleted) {

`setTimeout(コールバック, timeoutMs)` は「timeoutMsミリ秒後にコールバックを1回実行する」というブラウザ/Node.js標準のタイマー関数です。戻り値の `timeoutId` はこのタイマーを識別するIDで、後でキャンセルするために保存しておきます。`if (!isCompleted)` の `!` は否定（NOT）を表す演算子で、「isCompletedがfalseのときだけ中に入る」という意味です。つまり「まだ誰も決着をつけていなければ」という条件です。

if (defaultValue !== null) {
                    resolve(defaultValue);
                } else {

タイムアウトが発生したときの分岐です。呼び出し側が「タイムアウトしたらこの値で妥協してほしい」という `defaultValue` を渡していれば（nullでなければ）、エラーにせず `resolve` で正常終了として扱います。何も妥協案がない（nullが渡された）場合だけ `reject` でエラーとして投げます。

reject(`__ERROR__: ${operationName} timed out after ${timeoutMs / 1000} seconds`);

バッククォートで囲まれた文字列はテンプレートリテラルです。`${式}` の部分に変数の値がそのまま埋め込まれます（例: `timeoutMs / 1000` で秒数に変換）。`__ERROR__:` という接頭辞を付けているのは、このメッセージを受け取った呼び出し元やログ処理が「これはエラーだ」と文字列パターンで判別できるようにするためです。

operation
            .then(result => {
                if (!isCompleted) {

タイマーとは別に、引数で渡された `operation`（本来の処理）自体も並行して走っています。`.then(result => {...})` は「operationが成功したら、その結果resultを使ってこの中身を実行する」という意味です。ここでは、まだ未完了ならフラグを立てて、`clearTimeout(timeoutId)` でさっき仕掛けたタイマーを解除（無駄に発火させない）してから、本来の結果で `resolve` します。

.catch(error => {
                if (!isCompleted) {

`.catch(error => {...})` は `operation` が失敗（reject）したときに実行されます。この場合もタイマーを解除した上で、defaultValueがあればエラーをもみ消して代わりの値で成功扱いにし、なければ元のエラーをそのまま `reject` で伝播させます。エラーメッセージを勝手に書き換えず「元のエラーをそのまま渡す」というコメントの方針が、デバッグのしやすさを重視した設計であることが分かります。

今日覚えて帰ること

「タイマーvs本処理」のように2つの非同期経路が同じPromiseを解決しうる場面では、boolean フラグ（isCompleted）で「もう決着したか」を見張り、二重にresolve/rejectしないようにするのが定石です。自分で非同期処理を書くときもこのパターンを思い出してください。
