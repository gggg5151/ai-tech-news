anthropics/claude-code-action の src/mcp/path-validation.ts を読む

GitHub で実物を見る ↗2026.09.27

このリポジトリは、GitHub上のIssueやPRコメントでの指示を受けてClaude CodeがGitHubアクションとしてファイルを読み書きするツールです。AIがユーザーの投稿から「このパスのファイルを書き換えて」という指示を受け取る以上、そのパス文字列を鵜呑みにするとリポジトリの外のファイルを触られてしまう危険があります。今回選んだファイルは、まさにその「外部から来たパスを安全かどうか判定する」処理そのもので、60行に満たない短さながらセキュリティ上の判断がぎっしり詰まっているため教材に選びました。

コード

import { realpath } from "fs/promises";
import { resolve, sep } from "path";

/**
 * Validates that a file path resolves within the repository root.
 * Prevents path traversal attacks via "../" sequences and symlinks.
 * @param filePath - The file path to validate (can be relative or absolute)
 * @param repoRoot - The repository root directory
 * @returns The resolved absolute path (with symlinks resolved) if valid
 * @throws Error if the path resolves outside the repository root
 */
export async function validatePathWithinRepo(
  filePath: string,
  repoRoot: string,
): Promise<string> {
  // First resolve the path string (handles .. and . segments)
  const initialPath = resolve(repoRoot, filePath);

  // Resolve symlinks to get the real path
  // This prevents symlink attacks where a link inside the repo points outside
  let resolvedRoot: string;
  let resolvedPath: string;

  try {
    resolvedRoot = await realpath(repoRoot);
  } catch {
    throw new Error(`Repository root '${repoRoot}' does not exist`);
  }

  try {
    resolvedPath = await realpath(initialPath);
  } catch {
    // File doesn't exist yet - fall back to checking the parent directory
    // This handles the case where we're creating a new file
    const parentDir = resolve(initialPath, "..");
    try {
      const resolvedParent = await realpath(parentDir);
      if (
        resolvedParent !== resolvedRoot &&
        !resolvedParent.startsWith(resolvedRoot + sep)
      ) {
        throw new Error(
          `Path '${filePath}' resolves outside the repository root`,
        );
      }
      // Parent is valid, return the initial path since file doesn't exist yet
      return initialPath;
    } catch {
      throw new Error(
        `Path '${filePath}' resolves outside the repository root`,
      );
    }
  }

  // Path must be within repo root (or be the root itself)
  if (
    resolvedPath !== resolvedRoot &&
    !resolvedPath.startsWith(resolvedRoot + sep)
  ) {
    throw new Error(`Path '${filePath}' resolves outside the repository root`);
  }

  return resolvedPath;
}

引用はリポジトリの実物と機械で照合しています。「// …略…」は省略した行です。

上から順に読む

import { realpath } from "fs/promises";
import { resolve, sep } from "path";

Node.jsの標準モジュールから関数を読み込んでいます。`{ }`で囲むのは「名前付きインポート」で、そのモジュールが持つ複数の機能から必要な名前だけを取り出す書き方です。`fs/promises`はファイル操作系APIのPromise版（`await`で使える版）。`realpath`は、シンボリックリンクなどを全部たどった先の“本当の”絶対パスを返す関数です。`path`モジュールの`resolve`は複数のパス断片を結合して1つの絶対パスに正規化する関数、`sep`はOSごとのパス区切り文字（Windowsなら`\`、Mac/Linuxなら`/`）が入った定数です。

/**
 * Validates that a file path resolves within the repository root.
...
 * @throws Error if the path resolves outside the repository root
 */

`/** ... */`はJSDocと呼ばれる特殊な形式のコメントです。普通の`//`コメントと違い、エディタがこの関数にカーソルを合わせたときにポップアップで説明を表示してくれます。`@param`は引数の説明、`@returns`は戻り値の説明、`@throws`は「この関数はこういう場合にエラーを投げます」という注意書きです。呼び出す側は中身を読まなくても、このコメントだけで使い方と注意点がわかります。

export async function validatePathWithinRepo(
  filePath: string,
  repoRoot: string,
): Promise<string> {

`export`を付けると他のファイルからこの関数を`import`できるようになります。`async`が付いた関数は内部で`await`（後述）を使え、戻り値は自動的に`Promise`で包まれます。`Promise<string>`は「今はまだ結果がないが、いずれ`string`型の値が手に入る箱」を表す型です。引数の`filePath: string`のようにコロンの後に型を書くのがTypeScriptの型注釈で、ここでは「文字列以外を渡すとコンパイルエラーになる」という制約を付けています。

const initialPath = resolve(repoRoot, filePath);

`resolve`はパスの断片を順番に結合し、`..`（1つ上の階層）や`.`（現在の階層）を計算し尽くして1つの絶対パス文字列にする関数です。例えば`repoRoot`が`/repo`、`filePath`が`../../etc/passwd`なら、結合した上で`..`を計算し、`/etc/passwd`のような文字列になります。この時点ではまだファイルシステム上に本当にそのファイルがあるかは確認していません。あくまで文字列としての計算です。

let resolvedRoot: string;
let resolvedPath: string;

`let`は後から値を代入し直せる変数の宣言です。ここでは型だけ先に決めて（`: string`）、値は次の`try`ブロックの中で代入しています。関数の外の広いスコープで宣言しておくことで、複数の`try`ブロックをまたいで同じ変数を使い続けられるようにしています。

try {
    resolvedRoot = await realpath(repoRoot);
  } catch {
    throw new Error(`Repository root '${repoRoot}' does not exist`);
  }

`try { ... } catch { ... }`は「tryの中でエラーが起きたらcatchの中を実行する」という構文です。ここでの`catch`はエラーの中身を受け取る変数名を書いていません（`catch (e)`のようにも書けますが、中身を使わないなら省略できます）。`await`は「Promiseが解決するまでここで待つ」という意味です。`realpath`は指定したパスが実在しないと失敗（Promiseがreject）するので、リポジトリのルート自体が存在しない異常事態をここで検出し、`throw new Error(...)`で処理を中断してエラーを投げています。バッククォートで囲まれた文字列はテンプレートリテラルで、`${repoRoot}`の部分に変数の値が埋め込まれます。

try {
    resolvedPath = await realpath(initialPath);
  } catch {

今度は検証対象のパス自体に対して`realpath`を試みています。ここで失敗するのは「そのファイルがまだ存在しない」ケースです。Claude Codeは新規ファイルを作成する操作もするので、存在しないパスを即座にエラー扱いにはできません。コメントが示す通り、この場合は諦めずに一段階上の「親ディレクトリ」の実在チェックに切り替える、という設計判断がされています。

if (
        resolvedParent !== resolvedRoot &&
        !resolvedParent.startsWith(resolvedRoot + sep)
      ) {

ここがこの関数の核心のチェックです。「親ディレクトリの実パスが、リポジトリルートそのものと完全一致する」か「リポジトリルート＋区切り文字から始まっている」かのどちらでもなければ、リポジトリの外にあると判定します。単に`resolvedParent.includes(resolvedRoot)`のような緩い判定にすると、`/repo`というルートに対して`/repository-evil`のような紛らわしいパスまで“内側”と誤判定してしまいます。`resolvedRoot + sep`（例：`/repo/`）を接頭辞にすることで、そのような取り違えを防いでいます。`&&`は「両方の条件が真のときだけ全体が真になる」論理演算子、`!`は真偽を反転させる否定演算子です。

// Parent is valid, return the initial path since file doesn't exist yet
      return initialPath;

親ディレクトリが安全だと確認できたら、まだ実在しない`initialPath`（symlink解決前の、文字列として計算した絶対パス）をそのまま返しています。ファイルがないのでこれ以上symlinkを解決しようがない、という理屈です。

if (
    resolvedPath !== resolvedRoot &&
    !resolvedPath.startsWith(resolvedRoot + sep)
  ) {

ファイルが実在して`realpath`が成功した場合は、こちらの外側のチェックが実行されます。ロジックは先ほどの親ディレクトリのチェックと全く同じ形（一致するか、区切り文字付きの接頭辞になっているか）ですが、対象が「symlinkまで解決した本物の実体パス」である点が違います。たとえリポジトリ内の相対パス表記が安全そうに見えても、そのパスの正体がシンボリックリンクを通じてリポジトリ外の実ファイルを指していれば、ここで弾かれます。

今日覚えて帰ること

外部から受け取ったファイルパスを検証するときは、文字列の見た目（`../`が含まれるかなど）だけを見るのではなく、`realpath`のような関数で「実際にファイルシステム上のどこを指しているか」まで解決してから、安全なディレクトリのパス＋区切り文字を接頭辞として一致するか確認する、という一段深いチェックが必要になる。
