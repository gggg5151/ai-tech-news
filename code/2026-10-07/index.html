rakyll/hey の requester/requester.go を読む

GitHub で実物を見る ↗2026.10.07

`hey`はGoogleのJaana Burcu Dogan(rakyll)さんが作ったHTTP負荷テストツールで、Apache Benchの置き換えとして2万件以上のスターを集めています。コマンド一発で「同時にN本のリクエストを打ち続けて統計を取る」というシンプルな仕事をしていますが、中身はGoの並行処理の定番パターンが凝縮されています。今日は、指定した並列数ぶんのワーカー（リクエストを打ち続ける goroutine）を立ち上げ、全員の仕事が終わるのを待つ `runWorkers` 関数を読みます。

コード

func (b *Work) runWorkers() {
	var wg sync.WaitGroup
	wg.Add(b.C)

	tr := &http.Transport{
		TLSClientConfig: &tls.Config{
			InsecureSkipVerify: true,
			ServerName:         b.Request.Host,
		},
		MaxIdleConnsPerHost: min(b.C, maxIdleConn),
		DisableCompression:  b.DisableCompression,
		DisableKeepAlives:   b.DisableKeepAlives,
		Proxy:               http.ProxyURL(b.ProxyAddr),
	}
	if b.H2 {
		http2.ConfigureTransport(tr)
	} else {
		tr.TLSNextProto = make(map[string]func(string, *tls.Conn) http.RoundTripper)
	}
	client := &http.Client{Transport: tr, Timeout: time.Duration(b.Timeout) * time.Second}

	// Ignore the case where b.N % b.C != 0.
	for i := 0; i < b.C; i++ {
		go func() {
			b.runWorker(client, b.N/b.C)
			wg.Done()
		}()
	}
	wg.Wait()
}

引用はリポジトリの実物と機械で照合しています。「// …略…」は省略した行です。

上から順に読む

func (b *Work) runWorkers() {

これはメソッド定義です。`func` の直後にある `(b *Work)` は「レシーバ」と呼ばれ、このメソッドが `Work` という構造体に紐づいていることを示します。`*Work` の `*` はポインタという意味で、「`Work` の実体そのものではなく、その実体がメモリ上のどこにあるかを指し示す値」を受け取るということです。つまりこの関数は `Work` 型の値（この後出てくる `b.C` や `b.N` などのフィールドを持つ）を使って動きます。`b` はそのレシーバに付けた名前（Goでは self や this ではなく自由な名前を使います）。

var wg sync.WaitGroup

`var 変数名 型` という形の変数宣言です。`sync` パッケージの `WaitGroup` は「複数のgoroutine（Goの軽量スレッド）が全部終わるのを待つ」ための道具です。内部にはカウンターが1つあるとイメージしてください。初期値は0です。

wg.Add(b.C)

`wg.Add(数値)` でWaitGroup内部のカウンターを増やします。`b.C` は「レシーバ `b` の `C` というフィールド」で、このツールでいう並列数（同時に何本のワーカーを走らせるか）です。ここでカウンターを `b.C` まで増やしておくことで、「これから `b.C` 個のgoroutineが終わるのを待つつもりです」とWaitGroupに宣言しています。

tr := &http.Transport{
		TLSClientConfig: &tls.Config{
			InsecureSkipVerify: true,
			ServerName:         b.Request.Host,
		},

`:=` は「宣言と代入を同時に行う」書き方で、型を書かずに右辺の値から型を推論します。`&http.Transport{...}` は構造体リテラル（フィールド名: 値、の形でまとめて値を作る書き方）の前に `&` を付けたもので、「この構造体の実体を作り、そのポインタ（アドレス）を返す」という意味です。TLSClientConfigフィールドにも同様に `&tls.Config{...}` というポインタを渡しており、構造体の中に別の構造体（へのポインタ）をネストさせています。HTTP通信を行う際の低レベル設定（TCP接続の使い回し方やTLSの扱い）をここでまとめて作っています。

MaxIdleConnsPerHost: min(b.C, maxIdleConn),

フィールドの値に関数呼び出しの結果をそのまま入れています。`min(a, b)` はGoの組み込み関数で、2つの数値のうち小さい方を返します。並列数 `b.C` が大きくてもホストごとの待機コネクション数の上限 `maxIdleConn`（このファイルの別の場所で定義された定数）を超えないように、小さい方を採用しています。

DisableCompression:  b.DisableCompression,
		DisableKeepAlives:   b.DisableKeepAlives,
		Proxy:               http.ProxyURL(b.ProxyAddr),
	}

構造体リテラルの残りのフィールドです。`b.DisableCompression` や `b.DisableKeepAlives` は `Work` 構造体が持つ設定値（コマンドラインオプションなどで決まる真偽値）をそのまま転送しています。`Proxy: http.ProxyURL(b.ProxyAddr)` は、`http.ProxyURL` という関数を呼んで「常に指定したプロキシURLを使う」という振る舞いの関数を作り、それをProxyフィールドに渡しています（Transportのこのフィールドは「関数」を受け取る設計になっています）。最後の `}` で `http.Transport{...}` のリテラルが閉じます。

if b.H2 {
		http2.ConfigureTransport(tr)
	} else {
		tr.TLSNextProto = make(map[string]func(string, *tls.Conn) http.RoundTripper)
	}

`if 条件 { } else { }` という分岐です。`b.H2` が真（HTTP/2を使う設定）なら `http2.ConfigureTransport(tr)` を呼んで、作ったばかりの `tr`（Transport）をHTTP/2対応に書き換えます。そうでなければ `tr.TLSNextProto` に空のmapを代入しています。`map[string]func(string, *tls.Conn) http.RoundTripper` は「キーがstring、値が『stringと`*tls.Conn`を受け取り`http.RoundTripper`を返す関数』であるmap（辞書）」という型です。空のmapを入れることで、TLS接続後にHTTP/2へ自動アップグレードする仕組みを無効化し、確実にHTTP/1.1で通信させています。

client := &http.Client{Transport: tr, Timeout: time.Duration(b.Timeout) * time.Second}

ここまでで組み立てた `tr`（Transport）を使って、実際にリクエストを送る `http.Client` を1つだけ作っています。`time.Duration(b.Timeout) * time.Second` は、秒数を表す整数 `b.Timeout` を `time.Duration` という型に変換してから `time.Second`（1秒を表す定数）と掛け算し、「○秒」という時間の値にしています。このclientをこの後すべてのワーカーで使い回します。

for i := 0; i < b.C; i++ {
		go func() {
			b.runWorker(client, b.N/b.C)
			wg.Done()
		}()
	}

Goの基本的なforループ（初期化; 条件; 更新）で `b.C` 回繰り返します。ループの中の `go func() { ... }()` が今日のポイントです。`func() { ... }` は名前のない関数（無名関数）をその場で定義しており、末尾の `()` はその関数をすぐに呼び出すという意味です。その呼び出しの前に `go` を付けることで、「この関数呼び出しを新しいgoroutineとして並行に実行し、呼び出し元はその終了を待たずに次のループへ進む」という指示になります。つまりこのループは `b.C` 本のgoroutineを次々に起動するだけで、ループ自体はすぐ終わります。各goroutineの中では `b.runWorker(client, b.N/b.C)` を呼んで実際のリクエスト送信を1ワーカー分（全リクエスト数 `b.N` を並列数 `b.C` で割った本数）行い、終わったら `wg.Done()` でWaitGroupのカウンターを1減らします。無名関数は外側の `client`、`b`、`wg` をそのまま参照できます（これを「クロージャ」と呼びます）。

wg.Wait()

最後に `wg.Wait()` を呼ぶと、WaitGroupのカウンターが0になるまで（＝さきほど起動した `b.C` 本のgoroutineすべてが `wg.Done()` を呼び終わるまで）この行で処理がブロックされます。これにより `runWorkers` 関数は「全ワーカーが仕事を終えてから」初めてreturnします。goroutineを立てっぱなしにして関数が先に終わってしまう、という事故を防ぐ典型的な書き方です。

今日覚えて帰ること

「goroutineを複数立ち上げて、全員の終了を `sync.WaitGroup` の `Add` → `go func(){...; wg.Done()}()` → `Wait()` という3点セットで待つ」のがGoで並行処理をする時の基本形。この形を覚えておけば、自分でワーカープールを書くときにまず迷わなくなります。
