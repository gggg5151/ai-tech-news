evanw/esbuild の internal/helpers/waitgroup.go を読む

GitHub で実物を見る ↗2026.10.17

esbuildはGoで書かれた超高速なJS/CSSバンドラーで、内部で並行処理（goroutine）を多用しています。今回選んだwaitgroup.goは、標準ライブラリのsync.WaitGroupが持つ「AddとWaitを同時に呼ぶと危険」という制約を回避するために、わずか30行ほどで自作した代替実装です。標準ライブラリの弱点をどう正確に理解し、どう最小限の道具（atomicとchannel）で安全に回避するかという、実務でよく出てくる判断が詰まっている好例です。

コード

package helpers

import "sync/atomic"

// Go's "sync.WaitGroup" is not thread-safe. Specifically it's not safe to call
// "Add" concurrently with "Wait", which is problematic because we have a case
// where we would like to do that.
//
// This is a simple alternative implementation of "sync.WaitGroup" that is
// thread-safe and that works for our purposes. We don't need to worry about
// multiple waiters so the implementation can be very simple.
type ThreadSafeWaitGroup struct {
	counter int32
	channel chan struct{}
}

func MakeThreadSafeWaitGroup() *ThreadSafeWaitGroup {
	return &ThreadSafeWaitGroup{
		channel: make(chan struct{}, 1),
	}
}

func (wg *ThreadSafeWaitGroup) Add(delta int32) {
	if counter := atomic.AddInt32(&wg.counter, delta); counter == 0 {
		wg.channel <- struct{}{}
	} else if counter < 0 {
		panic("sync: negative WaitGroup counter")
	}
}

func (wg *ThreadSafeWaitGroup) Done() {
	wg.Add(-1)
}

func (wg *ThreadSafeWaitGroup) Wait() {
	<-wg.channel
}

引用はリポジトリの実物と機械で照合しています。「// …略…」は省略した行です。

上から順に読む

import "sync/atomic"

Goのファイルはpackage宣言の後にimportで使うパッケージを列挙します。sync/atomicは標準ライブラリで、複数のgoroutine（Goの軽量スレッド）が同じ変数を同時に読み書きしても壊れないようにする「アトミック操作（不可分な操作）」を提供するパッケージです。普通に`counter++`のような操作を複数goroutineから行うと、読み取りと書き込みの間に他のgoroutineが割り込んでデータが壊れる「競合状態」が起きますが、atomicパッケージの関数を使えばそれを防げます。

// Go's "sync.WaitGroup" is not thread-safe. Specifically it's not safe to call
// "Add" concurrently with "Wait"

`//`で始まる行はコメントです。ここでは「なぜこのコードが存在するのか」を説明しています。標準ライブラリのsync.WaitGroup（複数のgoroutineの終了を待つための定番の道具）は、実はAddメソッド（カウンタを増やす）とWaitメソッド（0になるまで待つ）を同時に呼ぶのは安全ではないとドキュメントに書かれています。esbuildのコードではその組み合わせが必要な場面があったため、自分で安全な版を作ることにしたわけです。コードを読むときは、まずこの「なぜ」を書いたコメントを読むと設計意図がすぐわかります。

type ThreadSafeWaitGroup struct {
	counter int32
	channel chan struct{}
}

`type ... struct { }`は複数のフィールド（データ）をひとまとめにした独自の型を定義する構文です。counterはint32型（32ビットの符号付き整数）で、現在未完了の処理の数を数えるカウンタです。channelはchan struct{}型で、「struct{}という型の値をやり取りするチャネル」を表します。struct{}はフィールドが一つもない空の構造体で、メモリを消費しないため「値そのものには意味がなく、送受信が起きたという事実だけが重要」なシグナル用途でよく使われます。

func MakeThreadSafeWaitGroup() *ThreadSafeWaitGroup {
	return &ThreadSafeWaitGroup{
		channel: make(chan struct{}, 1),
	}
}

これは「コンストラクタ関数」と呼ばれるパターンです。Goにはクラスのnewのような専用構文がないため、普通の関数で初期化済みの値を返すのが一般的です。戻り値の型`*ThreadSafeWaitGroup`の`*`はポインタ（値そのものではなく、値が置かれているメモリ上の場所を指す参照）を意味します。`&ThreadSafeWaitGroup{...}`は構造体のリテラル（その場で値を作る書き方）の前に`&`を付けることで、その構造体のポインタを作っています。`make(chan struct{}, 1)`はチャネルを作る組み込み関数で、第2引数の1は「バッファ容量1」を意味します。容量1があることで、受け取る側（Wait）がまだ呼ばれていなくても、送る側（Add）は1回だけブロック（処理が止まること）せずに送信できます。

func (wg *ThreadSafeWaitGroup) Add(delta int32) {

`func (wg *ThreadSafeWaitGroup) Add(...)`という書き方は「メソッド」の定義です。括弧の中の`wg *ThreadSafeWaitGroup`は「レシーバ」と呼ばれ、このAddメソッドがThreadSafeWaitGroup型の値（正確にはそのポインタ）に対して呼べることを示します。レシーバがポインタ型なので、メソッド内でwgのフィールドを変更すると、呼び出し元の元の値も変更されます（値型のレシーバだとコピーにしか影響しません）。delta int32は増減させたい量（終了待ちの数を増やすときは正の数、終わったときは負の数）を受け取る引数です。

if counter := atomic.AddInt32(&wg.counter, delta); counter == 0 {

`atomic.AddInt32(&wg.counter, delta)`は、wg.counterにdeltaを安全に（他のgoroutineと競合せずに）加算し、加算後の新しい値を返す関数です。`&wg.counter`の`&`はcounterフィールドのアドレス（メモリ上の位置）を渡すという意味で、atomic関数はポインタ経由でメモリを直接操作することで安全性を保証します。`if 文1; 条件 {}`という書き方はGo特有のイディオムで、セミコロンの前に変数counterを定義してから、その変数を使った条件判定を行います。このcounter変数はifブロックの中でだけ使える、スコープが絞られた変数です。

wg.channel <- struct{}{}

`チャネル変数 <- 値`という書き方はチャネルへの送信を意味します。`struct{}{}`は「空の構造体型の値を1つ作る」というリテラルで、先ほど説明した通りデータとしての意味は持たず「送信が起きた」という事実だけを伝えます。つまりここは「カウンタがちょうど0になった瞬間に、誰かが待っていればその人に知らせる信号を送る」という処理です。バッファ容量1のチャネルなので、まだ誰もWaitを呼んでいなくても、ここでブロックせずに信号を置いておけます。

} else if counter < 0 {
		panic("sync: negative WaitGroup counter")
	}

`else if`は最初のif条件が成り立たなかった場合に別の条件を試す構文です。ここではカウンタが0未満になった場合、つまりDoneがAddより多く呼ばれてしまったバグを検出しています。`panic(...)`はGoの組み込み関数で、プログラムに回復不能な異常が起きたことを知らせ、通常の処理を中断して即座にエラーを伝播させます。標準ライブラリのsync.WaitGroupと同じメッセージを使っているのは、利用者が見たときに「あのよく知られたエラーと同じ種類の間違いだ」とすぐわかるようにする配慮です。

func (wg *ThreadSafeWaitGroup) Done() {
	wg.Add(-1)
}

DoneメソッドはAddメソッドを-1を渡して呼ぶだけの薄いラッパーです。こうして「1つの処理が終わったことを知らせる」という使う側の意図を、名前として表現しています。中身のロジックを1か所（Add）にまとめることで、カウンタの増減ロジックが二重に書かれてバグの温床になることを防いでいます。

func (wg *ThreadSafeWaitGroup) Wait() {
	<-wg.channel
}

`<- チャネル変数`という書き方（送信と逆方向）はチャネルからの受信を意味し、何か値が送られてくるまでその場でブロック（待機）します。Addの中でカウンタが0になった瞬間に送信される信号を、ここで受け取ることで「全部終わるまで待つ」という動作を実現しています。複数のgoroutineが同時にAddとWaitを呼んでも、atomic.AddInt32がカウンタの操作を安全にし、チャネルが安全な待ち合わせの仕組みを提供するため、全体としてスレッドセーフになっています。

今日覚えて帰ること

標準ライブラリの型に「ここだけ安全でない」という制約があるとわかったら、全部を自作し直す必要はなく、atomic（安全な数値操作）とバッファ付きchannel（容量1の信号送受信）という2つの小さな部品を組み合わせるだけで、必要な部分だけpiece的に安全な代替を作れる。
