gosom/google-maps-scraper の exiter/exiter.go を読む

GitHub で実物を見る ↗2026.10.23

google-maps-scraperはGoogleマップから店舗情報を並行スクレイピングするツールです。検索キーワード(seed)ごとに複数の店舗(place)が見つかり、それぞれ非同期に処理が完了していきます。「全部終わったらスクレイピング処理を止める」という、並行処理では地味だけど難しい終了判定を、このexiterパッケージが1つの型に閉じ込めて担当しています。mutexと channel の組み合わせがコンパクトに出てくるので、Goの並行処理の実例として選びました。

コード

package exiter

import (
	"context"
	"sync"
)

type Exiter interface {
	SetSeedCount(int)
	SetCancelFunc(context.CancelFunc)
	IncrSeedCompleted(int)
	IncrPlacesFound(int)
	IncrPlacesCompleted(int)
	Run(context.Context)
}

type exiter struct {
	seedCount       int
	seedCompleted   int
	placesFound     int
	placesCompleted int

	mu         *sync.Mutex
	cancelFunc context.CancelFunc
	doneCh     chan struct{}
}

func New() Exiter {
	return &exiter{
		mu:     &sync.Mutex{},
		doneCh: make(chan struct{}, 1),
	}
}

// …略…

func (e *exiter) IncrSeedCompleted(val int) {
	e.mu.Lock()
	e.seedCompleted += val
	done := e.seedCompleted >= e.seedCount && e.placesCompleted >= e.placesFound
	e.mu.Unlock()

	if done {
		select {
		case e.doneCh <- struct{}{}:
		default:
		}
	}
}

// …略…

func (e *exiter) Run(ctx context.Context) {
	select {
	case <-ctx.Done():
		return
	case <-e.doneCh:
		if e.cancelFunc != nil {
			e.cancelFunc()
		}
	}
}

引用はリポジトリの実物と機械で照合しています。「// …略…」は省略した行です。

上から順に読む

type Exiter interface {
	SetSeedCount(int)
	SetCancelFunc(context.CancelFunc)
	...
}

Goの`interface`は「これらのメソッドを持っていること」だけを要求する型です。中身（具体的な構造体）を書かずに、外から見える操作一覧だけを宣言しています。こうしておくと、この後に出てくる`exiter`という具体的な実装を、呼び出し側は`Exiter`という抽象名だけ見て使えます。テストで別の実装に差し替えたり、将来実装を変えたりしやすくなるのがメリットです。

type exiter struct {
	seedCount       int
	seedCompleted   int
	placesFound     int
	placesCompleted int

	mu         *sync.Mutex
	cancelFunc context.CancelFunc
	doneCh     chan struct{}
}

`struct`はフィールドをまとめた型（他言語のクラスのデータ部分に近いもの）です。前半4つのint型フィールドで「探す対象のseed数」「終わったseed数」「見つかったplace数」「終わったplace数」を数えています。`mu *sync.Mutex`の`*`はポインタで、「Mutex本体そのもの」ではなく「Mutexがどこにあるかを指す矢印」を持つという意味です。`sync.Mutex`は複数のgoroutine（Goの軽量スレッド）が同じデータを同時に書き換えて壊してしまわないようにする鍵（排他制御）です。`chan struct{}`は「空の値（struct{}、何のデータも持たない型）だけをやり取りするchannel（goroutine間の通信路）」で、ここでは値そのものより「送られてきたという事実」だけを使う合図用です。

func New() Exiter {
	return &exiter{
		mu:     &sync.Mutex{},
		doneCh: make(chan struct{}, 1),
	}
}

`New`はこの型のインスタンスを作るためのコンストラクタ関数で、戻り値の型は構造体ではなく先ほどの`Exiter`インターフェースです。`&exiter{...}`の`&`は「このstructのポインタを作る」という意味で、フィールド名を指定して値を埋める書き方（構造体リテラル）です。`make(chan struct{}, 1)`はchannelを作る組み込み関数`make`の呼び出しで、第2引数の`1`は「バッファサイズ1」、つまり受け手がまだ読んでいなくても1個だけは送信側がブロックされずに送れる、という意味です。このバッファが後の非ブロッキング送信を成立させる鍵になります。

func (e *exiter) IncrSeedCompleted(val int) {
	e.mu.Lock()
	e.seedCompleted += val
	done := e.seedCompleted >= e.seedCount && e.placesCompleted >= e.placesFound
	e.mu.Unlock()

`func (e *exiter) IncrSeedCompleted(...)`の`(e *exiter)`はメソッドの「受信者（レシーバ）」です。`exiter`型の値に対して呼べる関数、という意味で、`e`はその値へのポインタとして関数内で使えます。処理の中身は、`mu.Lock()`で鍵をかけてから`seedCompleted`を増やし、「全seedが終わっていて、かつ見つかった全placeも終わっている」という完了条件を`done`という変数に計算し、`mu.Unlock()`で鍵を外しています。複数のgoroutineが同時にこのメソッドを呼んでも、Lockされている間は1つずつ順番に処理されるので、カウンタが壊れません。

if done {
		select {
		case e.doneCh <- struct{}{}:
		default:
		}
	}

注目すべきは、`done`の判定を`Unlock()`より前に済ませ、channelへの送信は`Unlock()`した後でやっていることです。鍵をかけたままchannelに送ろうとすると、受け手が詰まっている間ずっと鍵を握り続けてしまい、他のgoroutineがカウンタを更新できなくなる恐れがあるので、わざと鍵を外した後に送信しています。`select { case ...: default: }`はGoの`select`文の特殊な使い方で、「`e.doneCh <- struct{}{}`（channelへの空値送信）が今すぐできるならそれを実行し、できなければ（channelが満杯で待たされるなら）即座に`default`に進んで何もしない」という非ブロッキング送信です。バッファが1つあるので、1回目の送信はすぐ成功し、仮に複数のgoroutineが同時に`done`判定を通っても2回目以降は`default`に落ちて固まりません。

func (e *exiter) Run(ctx context.Context) {
	select {
	case <-ctx.Done():
		return
	case <-e.doneCh:
		if e.cancelFunc != nil {
			e.cancelFunc()
		}
	}
}

`Run`は呼び出し側が「完了を待つ」ために呼ぶメソッドです。ここでの`select`は先ほどと違い、2つの受信待ちのうち先に準備できた方を実行する使い方です。`ctx.Context`はGoで「いつ処理をやめるべきか」を伝える標準的な仕組みで、`ctx.Done()`はそのcontextが（タイムアウトや上位からの中断で）終了を知らせるためのchannelを返します。つまりこのselectは「外部から中断されたら(`ctx.Done()`)何もせず戻る」か「全作業完了の合図(`e.doneCh`)が来たら、登録されていた`cancelFunc`（他のgoroutineに停止を伝える関数）を呼ぶ」かのどちらか早い方を実行し、どちらも来るまでここでブロック（待機）します。

今日覚えて帰ること

複数のgoroutineで共有するカウンタを更新するときは、mutexで鍵をかける範囲を「判定に必要な最小限」にとどめ、channelへの送信など待たされる可能性のある操作は鍵を外した後にして、buffered channel + select-default の非ブロッキング送信で済ませると、処理が固まる心配がなくなる。
