MCP接続はなぜ危険になりうるか　4パターンと確認すべき7項目

報道qiita.com

MCP（Model Context Protocol）の仕様は、認可（authorization）を「任意」、人による確認（Human in the Loop）を「推奨」にとどめています。この記事は、接続しただけで即座に情報が漏洩するわけではなく、何を追加し、どこまで自動承認で動かすかという設定・運用によって被害の大きさが決まる、という立場から危険パターンを整理しています。

危険パターンはA:ツールポイズニング、B:間接プロンプトインジェクション、C:過剰な権限・長期キー、D:自動承認の4つに分類されています。実装調査では5.5%のMCPサーバーでツール説明文への指示の仕込みが検出され、53%が有効期間の長い固定キーに依存、88%が資格情報を必要とする一方でOAuth方式の採用はわずか8.5%にとどまるという統計が示されています。

実例として、2025年5月のGitHub MCPでは、攻撃者が公開リポジトリのissueにAI向け指示を埋め込むことで、非公開リポジトリの内容が公開プルリクエストに書き出される可能性が報告されました。記事はこれを「MCPサーバーのコード自体の欠陥ではなく、エージェントの仕組みの側で対処すべき設計上の問題」と指摘しています。また2026年8月には、AWSのAmazon MQ MCPにCVE（脆弱性の共通識別番号）CVE-2026-18655が割り当てられ、細工されたホスト名によりブローカーの資格情報とOAuthトークンが任意の宛先へ送信される可能性が報告されました。

接続前に確認すべき事項として、提供元とバージョンの確認、外部第三者が書き込み可能な場所からの読み込みの有無、追加スコープの決定、ツールと権限の最小化、キー保存場所と取り消し方法の確認、承認デフォルト設定の確認、承認画面が出ない実行方法での使用確認という7項目が挙げられています。

静的書き出しで4,710個の無駄ファイルを発見した話

体験談zenn.dev

小学生向けニュースサイト「こどもニュース」を運営する筆者が、Cloudflare Pages無料プラン（ファイル数上限20,000）の上限に近づいていた原因を調べたところ、Next.jsの静的書き出しで生成される、クライアント側遷移用のRSC（React Server Components）ペイロード（.txtファイル）の大半に誰もアクセスしていないことが分かりました。

2026年8月22日時点の実測では、全6,025ファイル中4,710ファイル、約78%がこの不要な.txtファイルだったといいます。記事を1日6本追加すると、対応前は1日あたり55ファイルが増える計算だったとのことです。

ビルド後処理で不要な.txtファイルを削除する対応を実施した結果、ファイル数は6,025から1,443に、容量は620MBから355MBに減少。ファイル数上限到達までの余裕期間は7か月から2年以上に延びたということです。

標準net/httpの薄いラッパー、GoのWebフレームワーク「Mach」

報道zenn.dev

Go 1.22以降で導入された標準net/http.ServeMuxのルーティング機能を土台に、薄い便利機能を追加したWebフレームワーク「Mach」を紹介する記事です。GinやEchoほどの大規模フレームワークは不要だが、素のnet/httpでは物足りない、という中間ニーズに応える選択肢として位置づけられています。

ルーティングは"GET /posts/{id}"のような記法で、パラメータ取得はc.Param("id")。GET・POST・PUT・PATCH・DELETEなどのメソッドヘルパーやJSON()・DecodeJSON()・Query()を含むContext APIを備え、ミドルウェアはGo標準のfunc(http.Handler) http.Handler形式に準拠しています。Zero dependencies（外部依存なし）、MITライセンスで提供されています。

記事内のベンチマーク（ns/op）では、Machが1943.8、Ginが1720.4、Echoが1843.0、標準ServeMuxが2400.2という結果でした。

ORM選定に迷ったらPoEAAの設計パターンに立ち返る

報道zenn.dev

TypeScript案件でORM（Object-Relational Mapper）を選ぶ際、Martin FowlerのPoEAA（Patterns of Enterprise Application Architecture）で紹介されているデータアクセス設計パターンを判断基準にすべきだと提案する記事です。「なんとなく流行っているから」で選ぶと、後で「思っていたのと違う」となるリスクを指摘しています。

記事が挙げるのはActive Record、Data Mapper、Table Data Gateway、Row Data Gatewayの4パターン。エンティティ自身が操作用メソッドを持つActive RecordにはTypeORMとSequelizeが、ドメインモデルとデータアクセス処理を分離しDDD（ドメイン駆動設計）向きのData MapperにはMikroORMが該当するとしています。

型安全性を重視するTable Data GatewayにはPrismaとDrizzleが該当し、Row Data Gatewayは現代のORMではあまり採用されていないと述べています。

コーディングエージェントの文脈圧縮、切り詰めるだけで忠実性を守る

公式arxiv.org

長時間稼働するコーディングエージェントは複数セッションにまたがり数百万トークン規模の文脈を扱う必要があり、限られたコンテキストウィンドウのためセッションをまたいだ圧縮（compaction）が必要になります。論文「CliffCompaction」（著者:Trang Nguyen、Eulrang Cho、Bingqing Chen、Tim Dettmers）は、圧縮対象の内容を言い換えたり書き換えたりせず、切り詰め（truncate）または削除（drop）のみで圧縮することで忠実性を保つ手法を提案しています。

この手法によりコストを最大50%削減でき、Terminal-Benchというベンチマークで10ポイント以上の性能改善が確認されました。KernelBenchでのCUDAカーネル高速化では、200ステップ時点で2.23倍、400ステップ時点で3.58倍の高速化が得られたとしています。

同じタスクを3回実行させたら4〜7割が食い違った、エージェントの再現性問題

公式arxiv.org

AIエージェントが同じタスクを繰り返し実行した際に回答が一致しない問題を扱った論文「Making Agents More Consistent」（著者:Travis Weber、Rohit Taneja）は、42種類のタスクを各3回ずつ実行したところ、モデルによって38%〜74%の割合で回答が一致しなかったことを確認しました。

これを解決するため、実行履歴から学習して決定的な処理を作る「スキル習慣化（skill habit formation）」という手法を提案。習慣化されたバリアントは456回の繰り返し実行で完全な一貫性を達成しつつ、通常の推論ベースの手法と同等の精度を維持し、トークン使用量は14〜56%削減、7〜53回の再利用でコスト面でも元の手法を上回るとしています。

ただしトレードオフもあり、ガード機構がパラフレーズされた入力の2.6%、境界的なケースの26%で問題のあるケースを許容してしまう精度低下が生じました。ルーティングとパラメータ抽出を分離することでエンドツーエンドの精度は0.952に向上し、コストは元の43%に抑えられたとしています。

コーディングエージェントにプロンプトを最適化させる「CASD」

公式arxiv.org

論文「Coding Agents are Strong Prompt Optimizers」（著者:Agamdeep Singh、Srishti Gautam、Priyanshu Gupta、Nikita Mehrotra、Tanmay Bakshi、Sumit Gulwaniの6名）は、静的な軌跡（トラジェクトリ）データセットのみからプロンプトを最適化する手法「Coding-Agent Skill Distillation（CASD）」を提案しています。環境への実行時アクセスや検証用データを必要とせず、コーディングエージェントに分析コードを書かせて統計を取り、失敗パターンを特定し、代表的なエピソードを検査させることで、洞察を行動ルールへと蒸留します。

著者らは、従来主流だった反復的な探索型プロンプト最適化は必須ではなく、「コーパス規模の統計的反省は反復探索の実行可能な代替手段」だと主張しています。ALFWorld、τ²-bench、SpreadsheetBench-Verifiedを含む4つのベンチマークで評価し、平均16.6パーセンテージポイントの改善で既存の最先端手法を上回りました。最適化プロンプト生成のコストは約1.60ドルで、検証ゲート付き探索より22倍以上安価だとしています。
