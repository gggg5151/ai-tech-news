Claude Codeに.envや鍵ファイルを消させないフックを自作

体験談zenn.dev

筆者(Oskra)はClaude Codeに作業を任せる際、確認プロンプトの多さに困り「確認なしで実行」設定を使っていたところ、AIが.envや.p8、.pemなどの鍵ファイルを誤って削除・移動するリスクに気づきました。特にApp Store Connectの鍵は1回しかダウンロードできず、消されると作り直しと利用箇所の全差し替えが必要になります。

これを防ぐため、Claude CodeのPreToolUse(ツール実行前に呼ばれるフック)として動くNode.jsスクリプト(~/.claude/hooks/secret-guard-mini.mjs、111行)を自作しました。コマンド実行前に引数のファイルパスを絶対パスに正規化し、鍵ファイルや.env関連ファイルへのrm/mv/cp/curl @等の危険操作を検出して終了コード2でブロックします。「"matcher": "Bash" は、Bashのコマンドのときだけ走らせる指定です」とし、settings.jsonに記述すれば全プロジェクトで有効になります。

deny(拒否ルール)のみの場合、危険な11パターンのコマンドのうち9通りをブロックできましたが、/bin/rmやpython3 -cによる削除は防げませんでした。deny+hook併用では10通りまでブロック数が増えましたが、python3 -c "import os; os.remove('.env')"のようなスクリプト経由の削除は依然防げず、著者はsandboxでの対応が必要だと述べています。検証環境はClaude Code 2.1.302、Node.js 22.22.2、Ubuntu 24.04(WSL2)です。

Next.js 14→15、fetchキャッシュのデフォルト反転に注意

体験談qiita.com

Next.js 14から15へのバージョンアップで発生したfetchキャッシュの挙動変更について、筆者(Cosoado)が自身のプロジェクト「NetaPair」で実際に直面した問題をもとに解説しています。v14まではキャッシュオプションを明示指定しなくてもforce-cache相当(キャッシュあり)として動いていたfetchのデフォルト挙動が、v15ではno-store相当(キャッシュなし)に反転した点が核心です。

移行チェックリストとして、認証済みユーザーの動的データなど毎回フレッシュに取得したい場合はcache: 'no-store'、定期更新が必要な場合はnext: { revalidate: 60 }、ビルド時に固定したい静的データはcache: 'force-cache'、ページ全体を動的化したい場合はexport const dynamic = 'force-dynamic'を使うべきとしています。

筆者はno-cacheとno-storeを混同して実装ミスをした経験があるとし、「毎回最新を取る」場合は必ずno-storeを使うべきだと強調しています。

LinuxカーネルCVE「PwnEscape」、KVMではなくネットワークスタックの欠陥

報道qiita.com

CVE-2026-99999(通称PwnEscape)について、筆者は「KVMの脆弱性ではなくLinuxネットワークスタックの脆弱性である」という主張を軸に、技術的な仕組みと影響範囲、各ベンダーの対応状況を整理しています。核心は、ゲストから送られる不正なチェックサムオフロードメタデータにより、ホスト側で検証済みのIPv4ヘッダが後から書き換えられてしまう欠陥です。

ip_do_fragment()でのフラグメント処理時の遅延書き込みにより、IHL値が20バイトから60バイトに変更され、論理的に28バイトのデータ領域から32バイトがホストメモリとして漏えいするとされます。CVSS(共通脆弱性評価システム)の基本値は9.3(Critical)、ベクターはAV:L/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:Hですが、一部のベンダー評価では8.8(PR:L)とされており、評価が分かれています。

ホストメモリ漏えいはVercelの本番Sandbox環境で実証確認され、ホストDoSとホストrootコード実行は研究者自身の環境での再現報告とされています。stable系列ではLinux 5.10.272以降、6.1.190以降などで修正が配布されています。筆者は「本稿は筆者個人の分析であり、所属組織や各事業者の公式見解ではありません」と明記しています。

LLMエージェントの長期記憶、削除後も情報が漏れ続ける

公式arxiv.org

arXivに掲載された論文「MemCut」は、LLMエージェントの長期記憶システムが「情報を正確に検索する能力」だけでなく「ユーザーの要求に応じて機密データを確実に削除(忘却)する能力」も備えるべきだと主張し、この忘却性能を測るベンチマーク「MemCut」を提案しています。456個の手設計された秘密データを長期対話に含め、削除後の復元可否を検証する注釈付き証跡を用意しています。

評価の結果、明示的な削除操作は表面的な復元(ネイティブ復元)を大幅に減らせる一方、別経路から情報が漏れ出す「残存復元」への効果は限定的で、削除指示の実行後でも39〜76%の割合で情報が復元されてしまうことが分かりました。原因として、削除すべき候補を網羅的に見つけられていない「候補カバレッジ」の低さが既存手法のボトルネックだと指摘されています。

考えている間に世界は変わる、エージェント評価の新基準

公式arxiv.org

論文「The World Won't Wait」は、LLMエージェントの推論・ツール呼び出しには時間がかかるため、考えている間にも環境が変化し続ける「ライブクロック」下では、判断時点で正しかった行動が実行時には有効性を失うという問題を扱っています。著者らは6種類のゲーム・180タスクからなる評価ベンチマーク「RealtimeBench」を導入し、高精度だが低速なモデル「GPT-6.1-sol」が、精度は劣るが高速なモデル「Jev」にリアルタイム環境では負けることを示しました。

さらに著者らは、遅い教師モデルが失敗を分析・検証し、速い生徒モデル向けに再利用可能な指示を生成する「TORSI」という二層構造の自己改善手法を提案しています。TORSIの適用によりJevの平均テストスコアは13.51から24.19に向上し、6種類すべてのゲームタイプで改善が確認され、生成された指示は他の3モデルにも転移可能だったとしています。
