RustマクロにC言語を直書きできるライブラリ「cinrs」

体験談zenn.dev

筆者は、Rustのマクロ内にC言語のコードをそのまま書けるライブラリ「cinrs」を開発し、GitHub上（tanakh/cinrs）で公開しました。マクロに書かれたCコードはプリプロセス・構文解析・意味解析を経て、外部のCコンパイラに依存せず正真正銘のRustコードへ変換されます。cinrs自体に完全なCコンパイラが実装されている点が特徴です。

c89からc23、GNU拡張のgnu89からgnu23まで複数の言語標準に対応し、__attribute__((cinrs_safe))でunsafeを取り除く安全性機能や、#[repr(C)]による構造体レイアウト対応、#includeなどのプリプロセッサ機能も備えます。setjmp/longjmp、スタック上の可変長配列、インラインアセンブリは未対応です。

ベンチマークではgccとの比較で0.927という結果が報告されており、C処理系と遜色ない性能とされています。著者は「当初はC99だけサポートしようと思っていた」と振り返っており、Rust安定版に必要な機能が揃ったことが開発の動機になったとのことです。

定石が通用しなかった医療データのdbtモデリング

体験談techblog.whitehealthcare.co.jp

ホワイトヘルスケア開発部データチームの石田氏は、レセプト（診療報酬明細書）データをdbt（SQLベースのデータ変換ツール）でモデリングする際、公式のベストプラクティスがそのままでは通用せず、医療データ特有の事情に合わせて設計を調整した経験を紹介しています。レセプトデータは医療機関の種類によって医科・DPC（診断群分類に基づく包括医療費支払い制度）・歯科・調剤の4つのファイル形式に分かれ、ファイル種別と識別単位の組み合わせでモデル数が約100パターンに達したといいます。

dbtの一般的な作法ではstaging層は軽い変換のみとされますが、同チームではフォーマット検査や保険者コード妥当性確認など通常より重いバリデーション処理を行いました。また1ソーステーブルにつき1つのstagingモデルという原則に反し、摘要情報にあたる複数のレコード種別を1つのstagingモデルに統合しています。

インクリメンタル戦略も、通常のupdated_atベースの方式から、請求年月とレセプトIDをキーに該当分を全件削除して再生成する独自方式へ変更しました。仕様通りでないデータの存在や、過去月分データが後から修正されて送られてくることが、医療データ特有の課題として挙げられています。

Cloudflare AI Gateway、予算ベースのAIモデル自動切替

体験談zenn.dev

Cloudflareのシニアソリューションエンジニアによる記事では、AI Gatewayの「Spend Limits」（コスト上限ルール）と「Dynamic Routing」（モデル自動フォールバック）を組み合わせ、LLM利用コストを予算内に収める実装方法が紹介されています。実装例では1日あたり100ドル（Claude Sonnet利用分）の予算を設定し、超過時にClaude Sonnet→Claude Haiku→Llama 3.2という3段階でモデルを自動的に切り替えます。

1つのゲートウェイに設定できるルール数は上限20件です。AnthropicやOpenAIのプロバイダは予算超過時にリクエストを制限しますが、Workers AIは予算に関わらず常にリクエストを通すfail-open仕様のため、最終フォールバック先として想定されています。キャッシュヒットしたリクエストはコスト0円として扱われます。

Spend Limitsはeventually consistent（結果整合性、変更が即時ではなく一定時間内に反映される特性）であり、一時的に予算上限を超過する場合がある点や、Dynamic Routingのフォールバックがコスト超過だけでなくプロバイダ障害時にも動作する点が説明されています。

GitHub API未認証レート制限、共有IPでの429リスク

体験談zenn.dev

筆者はVercel Functions上で稼働する自作Webアプリから、GitHub APIを未認証で呼び出しています。未認証リクエストの上限は60回/時間ですが、この制限は呼び出し元IPアドレス単位でカウントされる仕様です。Vercelのようなサーバーレス環境は複数の利用者・アプリで送信元IPを共有することがあるため、自分のリクエスト頻度が低くても他者の呼び出しと合算されて上限に達し、429エラーになりうると気づいたことを紹介しています。

「自分の呼び出し頻度と無関係に429が返りうる。『1時間に1回だから引っかからない』は、自分のリクエストだけを数えた見積もりでした」と振り返っています。対策として、API取得に失敗した場合は前回取得済みのデータを保持し続ける設計に変更したとのことです。

本記事は2026年9月1日時点の実測に基づくもので、筆者はまだ実際に429エラーを経験したわけではなく、運用を続けた上で追記する予定だとしています。対処法の一つとしてPersonal Access Token（GitHubの個人用アクセストークン）を使えば上限が5000回/時間に上がる方法もありますが、今回は未採用とのことです。

LLMエージェントのバックエンド生成に潜む「制約劣化」

公式arxiv.org

Francesco Dente氏らによる論文「Constraint Decay: The Fragility of LLM Agents in Backend Code Generation」は、LLMエージェントが統一APIコントラクトなどの構造的制約を満たしながらマルチファイルのバックエンドコードを生成する能力を検証しました。Flask、FastAPI、Djangoなど8つのウェブフレームワークにわたる計100タスク（グリーンフィールド生成80、機能実装20）で評価した結果、構造要件が積み重なるほど性能が大きく低下する「制約劣化」（constraint decay）現象を確認しています。

基準タスクから完全に要件を指定したタスクへ移行すると、アサーション合格率は平均27.28ポイント低下しました。中規模モデルはFlaskのような明示的で最小限のフレームワークでは機能しやすい一方、FastAPIやDjangoのような慣習重視の環境では大きく劣化するとのことです。失敗の主因はデータレイヤーの欠陥（不正なクエリ構成やORM〈オブジェクトとデータベースのテーブルを対応づける仕組み〉のランタイム違反）であり、機能要件と構造要件を同時に満たすことはコード生成エージェントにとって未解決の課題だと結論づけています。

注意機構の情報流トポロジーでハルシネーション検知

公式arxiv.org

arXivに投稿された論文「Detecting Hallucination in LLMs: Tracing the Topological Signatures of Impaired Context Sharing」は、LLMのハルシネーション（幻覚、事実に基づかない出力）を検出する新手法を提案しています。注意機構（attention）グラフ内の情報流パターンの位相構造を、Forman-Ricci曲率という指標で分析し、情報のボトルネックを検出することで幻覚を含む応答と含まない応答を区別します。

この手法は単一パスで動作するため、複数回応答を生成して比較する既存手法より効率的だとされています。分析の結果、幻覚を含む応答は特に最終層でトークン間の文脈共有が阻害されており、自己注意への過剰依存、文脈検索の拡散、情報の過剰圧縮といった特徴が見られたとのことです。複数のLLMとベンチマークで一貫した性能向上を確認したとしています。

LLM強化学習をFP8精度で安定化する新手法「Calibrated Clipping」

公式arxiv.org

論文「Towards Full Pipeline FP8 Reinforcement Learning for LLMs」は、LLMの強化学習訓練パイプライン全体をFP8（8bit浮動小数点、通常のBF16より精度が低いが計算が高速な数値形式）精度で実行しようとすると、量子化ノイズが方策の重要度比を歪め、信頼領域外と誤判定されたトークンの勾配がゼロになり、訓練が不安定化する（エントロピーの急増やエラー出力）という問題を指摘しています。

この原因を分析した上で、BF16での分布に合わせてFP8のクリッピング境界を動的に調整する「Calibrated Clipping」という手法を提案。強化学習の2つのアルゴリズム（GRPO・DAPO）で検証し、BF16ベースライン相当の性能を回復できることを示しました。
