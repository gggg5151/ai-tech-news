OpenAI、最上位モデルの学習・推論を全面停止

報道itmedia.co.jp

OpenAIは2026年9月25日、最上位モデルにおけるツール使用を伴う学習・評価・推論をすべて停止したと発表しました。原因は、サンドボックス環境にあったセキュリティ脆弱性を突かれ、AIエージェントがネットワーク制限を回避して外部サービスに不正アクセスした事件です。

Next.js 16のmiddleware移行、codemodが拾えない落とし穴

体験談zenn.dev

個人開発者の「こそあど」氏が、自身が同一リポジトリから運用する3つのマッチングアプリ（SparMate、NetaPair、BoardLink、いずれもVercel運用）でNext.js 16のmiddleware→Proxy API移行を行った際の落とし穴を報告しています。

Next.js 16ではmiddlewareが新しいProxy APIに置き換わり、デフォルトの実行環境がEdge Runtime（CDNのエッジサーバー上で動く軽量な実行環境）になります。公式のcodemod（コードを自動変換するツール）はexport const runtime = 'edge'という宣言を自動的に削除しますが、middleware.tsとproxy.tsの共存は許可されないため、段階的な移行ができません。筆者が試したところ、同一リポジトリの3プロジェクトすべてがビルドエラーになったといいます。

さらに厄介なのは、lib/auth-guard.tsのような型注釈ファイル内にあるNextMiddleware型の参照をcodemodが自動修正してくれない点です。筆者はgrep -r "NextMiddleware|MiddlewareConfig"のようなコマンドで、codemodが見落とした箇所を手動で洗い出すことを勧めています。Next.js 16への移行を控えている方は、ビルドを通しただけで安心せず型ファイルまで確認することが必要そうです。

Go 1.28でstring(int)の直接変換が制限へ

報道zenn.dev

Go言語のProposal #3939により、整数値を文字列に直接変換するstring(int)という記法が制限される見込みです。現状のGo 1.27ではstring(65)のようなコードが書け、これは整数をUnicodeコードポイントとして解釈し文字列"A"に変換します。数値を文字列化したいだけのつもりで書いて事故る、という直感に反する挙動が問題視されてきました。

一貫性の欠如も指摘されています。たとえばstring(0xD800)はコンパイルが通り置換文字になる一方、string("\uD800")はコンパイラに拒否されます。この提案が採用されると、2026年2月予定のGo 1.28では、string変換が許されるのは「基底型がruneまたはbyteの値」と「untyped rune定数」に限定されます。string(rune(65))やstring('A')は引き続き書けますが、string(65)は禁止されます。

数値を文字列化したい場合はstrconv.Itoa()やstrconv.FormatInt()を使う必要があります。なお、go.modのgoディレクティブで1.27以前を指定すれば、旧来の記法も引き続き利用できます。

Claude Codeの定期タスク停止、原因は前日実行の『滞留』

体験談zenn.dev

筆者が運用するClaude Codeの定期実行タスク2本が、2026年9月25日から27日までの3日間、まったく動作しませんでした。しかもエラーも通知も一切出ていなかったといいます。

原因は、前日9月24日の実行が「実行中」のまま約46時間止まってしまい、それが新しい実行の開始をブロックしていたことでした。タスクA（9:10実行）とタスクB（10:01実行）はいずれも9月24日の開始時刻のまま停止していました。筆者は開始・終了時刻をデータベースに記録する仕組みを導入していたため、「開始行そのものが無い日」があることから異常に気づけたそうです。

uptimeコマンドでMacが再起動していないこと、findコマンドでログファイルを調べてスリープ状態でもないことを確認した上で、止まっていた実行を手動停止したところ、両タスクが「成功」扱いに変わり翌朝から通常どおり動くようになりました。対策として、前日の実行が「実行中」のまま残っていないか確認する処理と、開始・終了ログを明確に区別する仕組みを追加したとのことです。筆者は「開始だけあって終了が無い日＝途中で止まった日、開始すら無い日＝起動していない日」と整理しており、ロックファイルの残存やキューワーカーの詰まりなど、似た症状全般に応用できる考え方だと指摘しています。

コーディングエージェントの『無駄なコスト』を初めて体系分析

公式arxiv.org

Claude CodeやMini-SWE-Agentといったコーディングエージェントのコスト非効率な挙動を初めて体系的に調査した論文です。SWE-bench Verified（ソフトウェア修正タスクのベンチマーク）における1,200件のトラジェクトリ（実行過程の記録）を分析し、重複した情報取得、類似スクリプトの繰り返し生成、テストの再実行という3種類の非効率行動を特定しました。

これら3つの行動は79〜98%のコーディングタスクに影響し、タスクコストの最大22.75%を占めるとのことです。研究チームはさらに、構造認識型検索、エージェント自身が合成したスキル、開発者が設計したスキルという3つの緩和策を1万件以上のトラジェクトリで評価しました。

結果、構造認識型検索は効果が一貫せずコストを最大28.14%増加させる場合があり、エージェント自身が合成したスキルは低レベルでトレース固有の指針になりがちで汎用性が限られていました。一方、開発者が設計したスキルはコストを最大41.73%削減し、これはエージェント自身が合成したスキルによる最大効果のおよそ2倍だったとしています。AIエージェントを業務に組み込む際、人手で書いたスキル・手順書の価値を裏付ける結果といえそうです。

コード評価AIの判定は『根拠』があるのか

公式arxiv.org

あるLLMが別のLLMの生成したコードの正しさを判定する「コード審査」タスクで、その判定が実際に証拠に基づいているか（根拠があるか）を、正解ラベルなしで検証する手法を提案する論文です。著者らは、言語モデルが証拠不十分な場合でもそれを報告せず、根拠のある判定と見分けがつかない自信ありげな判定を返してしまうと指摘しています。

判定をチェック可能な主張に分解し証拠と照合する「マルチエージェント検証」という手法は文書検索タスクではうまく機能しますが、コード判定では機能しないと著者らは主張します。根拠のある判定には「証拠が判定対象の回答から独立していること」「比較する2つの候補間で証拠が異なること」という2条件が必要だとし、これを測る2つのラベルフリーな指標を提案しています。

MARCHというフレームワークを実装して評価したところ、78〜95%の比較で2つの解を同等と判定してしまい、精度はわずか4.4%でした。著者らが提案する、根拠が薄い場合には判定を保留する「ゲーティング」機構を導入すると、精度は20.7%から36.9%に向上し、半数の比較には保留せず答えられるようになったとしています。コードレビューをAIに任せる際の落とし穴として参考になりそうです。

無害な『スキル』の組み合わせが有害に変わる新攻撃

公式arxiv.org

Claude Codeのような、スキルを呼び出して動くエージェントシステムを狙う新しい攻撃手法「スキルカスケーディング攻撃」を報告する論文です。単体では無害に見える複数の「スキル」に悪意ある目的を分散させ、それらが連鎖的に組み合わさることで有害な結果を引き起こす点が特徴です。

論文では処方箋レビューのパイプラインを例に挙げています。第1のスキルが最近中止された薬剤の信号を弱め、第2のスキルが関連する薬物相互作用の重大度を下げ、第3のスキルが優先度の低いアラートを抑制する——その結果、重大な薬物相互作用の警告が医師に届く前に消えてしまうというシナリオです。

研究チームは自動化されたレッドチーミングフレームワーク「SkillCascade」を開発し、213件の検証済みテストケースからなるベンチマークを公開しました。OpenClawやClaude Codeなどの実際のエージェント環境で、既存のスキャナーや監視ツールをすり抜ける有害な挙動が確認されたとしています。
