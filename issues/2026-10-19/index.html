Gemini 4 Argonの「100万トークン」は入出力共有という実態

報道qiita.com

Gemini 4 Argon（Google）のコンテキスト上限は1,048,576トークンですが、これは入力専用の枠ではなく、入力・思考（推論）・出力を合わせた単一のコンテキストウィンドウで共有される値だと、公式情報をもとにした解説記事が整理しています。通常実行時の最大出力は65,536トークンで、100万トークンを入力した上にさらに100万トークン出力できるわけではない点が注意点として挙げられています。

Claude Code自身のコードの9割がAI生成、レビューも7段階のAI主導に

報道note.com

Anthropic社内では、Claude Code自身のコードの約90%がClaudeによって生成されており、2026年6月から9月の間にマージ済みプルリクエスト数は2倍以上、主要モノレポの1日あたり変更数は約2,500件から3万件以上に増加しました。一方で変更を取り消すリバート率は40%以上低下しているといいます。

この急拡大に対応するため、Anthropicは「人間がコードを読んだか」ではなく「何が壊れる可能性があり、どの検査が適切か」を基準にする方針へ転換しました。PR作成前の別AIによるレビュー、複数AIが並列で問題を探し別のAI群が指摘の妥当性を判定する段階（実質的なレビューコメントが付くPRの割合を16%から54%に向上）、セキュリティ専用レビュー、CI（継続的インテグレーション、変更ごとに自動でビルド・テストする仕組み）による自動チェックという流れで構成されています。

人間の承認はリスク別に分けられ、低リスク（文言修正など）は0人、中リスク（通常の機能変更）は1人、高リスク（危険度の高い変更）は2人の承認が必要とされています。実際に50回以上の修正往復が発生したPRもあったため、3回のレビュー後は実装方針そのものを再検討し、同じ指摘の繰り返しを禁止するルールが設けられました。「AIの承認は、人間の承認として数えられません」という原則も明記されています。

SupabaseのRLSは正しくても、GRANTだけが開いていた

体験談zenn.dev

Next.js App Router + Supabase + Tailwind CSS製アプリ「Hubpin」を開発する筆者は、デモログイン機能の公開直前、public.profilesテーブルでRLS（Row Level Security、行単位のアクセス制御）自体は正しく設定されていたにもかかわらず、プロフィール編集用のUIを一つも作っていないテーブルのupdate権限がauthenticatedロールに対して開いたままになっているのを発見しました。

想定される攻撃経路は、デモログインでセッションを取得し、DevTools（ブラウザの開発者ツール）からアクセストークンを抜き出してSupabaseのREST APIへ直接PATCHを送るというものです。これによりusername変更によるURLの永続的な破損や、display_nameの書き換え（落書き）が公開ページに表示される被害が起こり得ました。さらにデモアカウントのリセット処理はitemsテーブルのみを初期化する仕様だったため、profilesへの改ざんは残ってしまう設計上の穴もありました。

修正は、まずrevoke文で全体のupdate権限を撤回した上で、更新を許可する列（display_nameなど）を明示的に指定したGRANT文に書き換えるというものです。筆者は「UIが存在しないテーブル・カラムでも、DB側の権限が開いていればAPI経由で直接操作され得る」という教訓を共有しています。

Next.js devサーバーが無反応になったら.nextを消す

体験談zenn.dev

Next.jsの開発サーバーで、ボタンやフォーム操作への反応が消え、コンソール出力も出なくなる現象が報告されています。原因は.next/static/chunks/ディレクトリが空になり、Reactクライアントが起動できずSSR（Server Side Rendering、サーバー側でHTMLを生成する方式）のHTMLだけが表示された状態になることで、HMR（Hot Module Replacement、コード変更を即時反映する仕組み）のリビルドが中断されると発生しやすく、devサーバーの長時間連続稼働やブラウザ自動化ツールの使用時に起こりやすいといいます。

診断にはDevToolsのNetworkタブで_next/static/chunks/*.jsが404を返していないか確認する方法が有効です。解決策は「rm -rf .next && npm run dev」の実行で、筆者は1分以内に復旧できたと述べています。

Claude、NSAが残した暗号曲線「25年来の謎」を30分で解明

報道japan.cnet.com

米国立標準技術研究所（NIST）が2000年に公表した電子署名規格ECDSA（楕円曲線デジタル署名アルゴリズム）で使われる楕円曲線には「シード」という数値が記載されていましたが、これを提供したNSA（米国家安全保障局）は生成方法を公表しておらず、意図的に弱点を持つ曲線が選ばれたのではという懸念とともに25年以上謎とされてきました。

Anthropicの社員が社内の研究モデルにシードの由来を調べるよう依頼したところ、Claudeは30分足らずでNISTの5つの曲線のシード生成方法を特定しました。C言語ライブラリの疑似乱数生成機能「lrand48」を使い、1997〜98年の日付と時刻を数値化した値を初期値として生成したものだったといいます。Claudeは別の規格の5つの曲線やNIST採用の別4つの曲線についても同様に生成方法を特定しました。

これにより、元NSA担当者が記憶していた「英文をハッシュ化した」という説は誤りだったことが判明しました。Anthropicは新たな攻撃方法や曲線の弱点が見つかったわけではなく、むしろ単純な方法で生成されていたことから意図的な弱点が仕込まれていた可能性は低くなったとし、利用者側の対応は不要と説明しています。一方で、採用されなかった候補の選定理由や「B-163」のシードなど一部の謎は依然解明されていません。
