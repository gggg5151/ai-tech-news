Claudeが大規模形式検証を実践、Theoremと協業

体験談anthropic.com

2026年10月22日に公開された記事によると、AnthropicとTheorem社の協業チームはClaude(Opus 5.5など)を用いて、123のオープンソースライブラリにある239のエントリーポイントについて機械語レベルの形式証明(プログラムの性質を数学的に証明する手法)を行いました。証明に使われたコードは証明言語Rocqで記述され、総量は約1億8千万行に達しています。これまで専門家が多年かけて行っていた作業を、LLMが大規模かつ現実的なコストで実行できることを示した研究です。

対象となったのはOSS-Fuzz、AddressSanitizer、RISC-Vなど、セキュリティ検証やファジングに関連するツール・環境です。証明プロセスの中で、libexpatに関する未検出のバグ(CVE-2026-56132)も発見されたと報告されています。

効率面では、Opus 5.5が前世代モデルに比べて40%少ないトークン数で証明を完了できたほか、既に作られた証明を再利用することでさらに17%のトークン削減効果があったとしています。本研究はAnthropicのFrontier Red Teamを含む研究チームとTheorem社の協業者、合計15名の共同著者によって行われました。「LLMは今、証明済みのセキュリティ保証を含む新しいソフトウェア開発ワークフローを可能にする規模で、形式証明を生成できる」と評されています。

OpenAI公式、10億ユーザーを支える自社ストレージ基盤「Habitat」

公式openai.com

OpenAI公式ブログのPart IIでは、ChatGPTの10億人超のユーザーを支える独自オンラインストレージプラットフォーム「Habitat」の内側が解説されています。HabitatはAzure Cosmos DBを基盤に構築され、「信頼性→パフォーマンス→効率」の順で進化させてきたとされています。現在500ペタバイト以上のデータを保有し40の地理的地域をサポート、最大規模のアカウントは月間2,000万以上のQPS(Queries Per Second、1秒あたりのクエリ数)を処理しているといいます。

マルチテナンシー設計は、単一共有コンテナ(ノイジーネイバー問題発生)→ワークロード分離による単一テナント化(容量計画の課題)→改善されたマルチテナンシーへの回帰という3フェーズを経て変遷してきました。グローバル読み取りレイテンシは約120msから約10msへ、約12倍改善されたとしています。読み取りリクエストが全体の90%以上を占め、変更データキャプチャ(CDC、データ変更をリアルタイムで捕捉する仕組み)は毎秒数百万の変更を処理しているとのことです。

システムはPythonからマルチリージョン対応へ移行し、サービス層はRustで書き直され、Valkeyベースの分散キャッシュ層が統合されました。2024年後半にはプライマリリージョンの停電によるフェイルオーバーが発生し、フェイルバック時に「接続スタンピード」が起きゲートウェイが過負荷になった経緯も紹介されています。OpenAIは現在、RocksDB CloudとRaftベースのレプリケーションを用いた、エクサバイト規模の社内製オンラインストレージシステムの開発も進めているとしています。

Lambda Web Functionsで実測、Next.jsの同時アクセス・キャッシュ・費用

体験談zenn.dev

筆者(km氏)が2026年10月、AWSの新機能「Lambda Web Functions」上でNext.js(v16.4.2)を動かし、従来の「Lambda Event Functions」(Lambda Web Adapter使用)やALB+ECS(Fargate)と比較しながら検証した記録です。コールド状態で50同時アクセスをかけた場合、Web Functionsは6環境で処理できたのに対し、Event Functionsは1環境1リクエストしか処理できず50環境が必要でした。短期間の負荷試験では、Web Functionsは1環境あたり最大2件を同時処理しました。500ミリ秒の待機を伴うテストでは、Web Functionsの環境数は36環境まで増加しました。持続的な負荷では、1環境が処理するリクエスト数が最大20件まで上昇する傾向も確認されています。

Next.jsのキャッシュ機構についても検証されています。"use cache"は環境ごとのメモリにのみ存在し複数環境間で共有されず、revalidateTagも受け取った1環境にしか効果が及びません。キャッシュの前提を誤ると意図しない挙動につながる点が示されています。

費用面では、月100万リクエスト・I/O待機150ミリ秒の想定で、Web Functionsが約2.80ドル、Event Functionsが約2.00ドル、ALB+ECS最小構成が約31.00ドルと試算されています。待機時間が500ミリ秒になると、Web Functionsは約14ドル、Event Functionsは約7ドルに上昇します。デプロイはGitHub Actionsから「aws lambda-web deploy」の1コマンドで完了し、コンテナイメージの作成が不要な点も紹介されています。

TypeScript 7.1「Content Mappers」で.graphqlファイルを直接型付け

体験談zenn.dev

TypeScript 7.1で追加されたContent Mappers機能を使い、Next.jsプロジェクトで.graphqlファイルを中間生成物なしに直接インポート・型付けする方法を解説する記事です。コンパイラが未知の拡張子に遭遇すると、指定した外部プロセスをJSON-RPCで起動し、仮想のTypeScriptコードを受け取って型解決します。この型解決は物理ファイルを生成せず、すべてメモリ上で行われます。

従来のgraphql-codegenには、codegenのwatchプロセスを常駐させる必要がある、生成ファイルによってGitの差分が肥大化する、型エラーの表示が遅延するといった課題がありました。Content Mappersではこれらが解消され、.graphqlファイルを編集して保存した瞬間に、再ビルドやwatchコマンドの待機なしに最新の型が反映されます。「tsc --runExternalCode --noEmit」を実行するだけで、中間生成ファイルなしにクエリと引数の型が厳密に検証できる点が紹介されています。

数億件テーブルの部分削除、Goバッチで安全に進める運用設計

体験談zenn.dev

日本トレカセンターのバックエンドエンジニアが執筆した記事で、サービス運用で蓄積された役割を終えたデータを、数億件規模のMySQLテーブルから部分削除する運用設計を解説しています。削除対象がインデックスで絞り込めないため、まずBigQueryで削除対象IDを抽出し、IDを分割してS3にmanifest.json+part-*.csv.gzの形式で圧縮保存します。

Goで実装された定期バッチがこの分割ファイルを読み込んで検証し、IDを小分けにしてMySQLから削除を実行します。設計の中心は、削除処理と進捗保存を同一トランザクションで確定させることです。これにより処理が中断しても、次回実行時に続きから処理を再開できます。ファイルの分割単位とトランザクションの分割単位は分離されており、読み込み方法とDB処理量を独立して調整できる点も特徴です。

S3 Batch OperationsやStep Functionsの利用も検討しましたが、最終的には既存のバッチ処理基盤での実装を選択したとのことです。「削除と進捗を一緒に確定させ、次の実行で続きを処理できることを設計の中心に置きました」と振り返っています。

DynamoDBのGSI設計、書き込みコストをWCUで数値化して比較

報道zenn.dev

Go/クラウドインフラを専門とするソフトウェアエンジニアによる記事です。DynamoDBのGSI(グローバルセカンダリインデックス、メインテーブルとは別のキーで検索を可能にする仕組み)はアクセスパターンを満たすために追加するものですが、追加した分だけWCU(書き込みキャパシティユニット)が増えるというトレードオフがあります。著者は「メインテーブルのキーで解けないアクセスパターンのみGSI候補にすべき」「GSIのキー属性が変わると索引への書き込みが2回分になる」「ALL射影は索引のキーに含まれない属性の更新まで書き込みに波及する」という3点を指摘しています。

注文管理システムを例に、GSIなし(D0)、全属性射影のGSIを2本追加(D1)、射影を絞りスパース化したGSI(D2)の3パターンで、注文作成から状態遷移3回・メモ更新2回までのライフサイクルにおける消費WCUを比較しています。結果はD0が合計12、D1が合計42(D0の3.5倍)、D2が合計20(D1から約52%削減)となり、設計次第で書き込みコストが大きく変わることを数値で示しています。

著者はこの比較モデルについて「DynamoDB本体の実装検証ではなく、課金ルールの解釈に基づくモデルである」と明記し、実環境ではReturnConsumedCapacityを使って実際のWCU消費量を確認するよう勧めています。

系列圧縮を回帰問題として再定義する「テスト時回帰」

公式arxiv.org

論文「Rethinking Sequence Compression with Test-time Regression」は、従来のプーリングや学習済み射影によるシーケンス圧縮に代わる手法「テスト時回帰(TTR)」を提案しています。入力トークン列を回帰問題として定式化し、その回帰係数を圧縮表現として使うというアイデアです。回帰問題自体は逆伝播によってend-to-endで学習されますが、推論時には係数を前向きパスで閉形式に高速計算できます。

著者らが提案する実装「TTR-Compressor」は、ブロック単位のスパース注意でのRULERベンチマーク性能を大幅に改善したほか、マルチモーダルLLMの視覚トークンマージングにおいて、視覚トークン数を55.6%削減しつつ標準的なMLPマージャーと同等の性能を達成したと報告されています。

推論モデルの'wait'は強化学習が生んだのか、起源を追う研究

公式arxiv.org

論文「Inherited, Not Invented: Tracing the Provenance of Wait in Reasoning Models」は、推論モデルが出力中に使う「wait」というマーカーについて、強化学習(RL)がそれを生み出したという通説に反論するものです。著者らは訓練履歴の追跡や注入エラーテスト、MATH-500での精度測定を通じて、OLMo-3やMiMoなど複数のオープンソースモデルを分析しました。

その結果、「wait」マーカーはRLが新たに発見したものではなく、事前の訓練データに由来して継承されたものであり、RLはその頻度を増幅するだけだと結論づけています。ゼロRL環境(強化学習を一切行わない条件)ではこのマーカーはほとんど出現せず、マーカーの出現頻度だけではRLによって誘発された推論の良し悪しを測る指標にはならないとしています。また、自動ジャッジを用いた評価手法自体にも信頼性の懸念があると指摘しています。
